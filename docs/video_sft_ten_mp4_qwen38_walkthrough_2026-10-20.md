# 用 10 个 MP4 和一个 Qwen3.8-Flash API 走一遍数据构造

日期：2026-10-20。本文是具体流程讲解；文件名、内容、时长、题量与通过数均为虚构示例，未读取实际视频、未调用用户 API。整体实现仍处于设计阶段。

**当前v1：A4移除；模块4只通过或reject，不补看、不修复、不回流重生成；A10不启用，CoT仍待定。**

## 1. 先明确：你给什么，程序和模型各做什么

你提供一个 MP4 文件夹和一个可用 API 的配置：模型 ID、endpoint、密钥引用。程序另有固定配方，例如中文出题、OE/单选、分辨率与预算。密钥不写进训练数据或日志。

```text
你提供：10个MP4 + qwen3.8-flash接口

本地程序：读文件、取帧、记录时间、调用模型、保存结果、检查格式、去重与统计
Qwen API：看画面写描述、读描述出题、构造CoT（方法待定）、一次综合审核候选
```

保留的A1/A2/A3/A5/A6/A7是不同工作指令，**可以全部使用同一个qwen3.8-flash，无需按角色配多套模型或账号**。编号沿用旧设计，A4已取消，不需要补齐号码。

官方文档列明 `qwen3.8-flash` 支持 Image/Text/Video 输入、Text 输出。[模型能力来源](https://help.aliyun.com/zh/model-studio/qwen3-8-flash) 实际 endpoint 的媒体传输、限制与可用能力仍须接入时验证。下面主要用“程序取帧 → 发送有序图片与时间”的方式解释，便于沿用 LLaVA caption 逻辑；不依赖 API 自动采样行为。

远程 API 不能仅凭一个普通本地目录路径读取你电脑中的文件。程序负责按服务支持的方式编码/上传媒体；本地路径属于程序的配置。我们只使用画面，MP4 音轨不进入模型输入。

## 2. 这 10 个视频假设长什么样

```text
<你的MP4目录>/
  v01.mp4  v02.mp4  v03.mp4  v04.mp4  v05.mp4
  v06.mp4  v07.mp4  v08.mp4  v09.mp4  v10.mp4
```

| 文件 | 为讲解假设的内容 | 时长 | 预清理结果 |
|---|---|---:|---|
| v01 | 倒水、搅拌、收拾桌面 | 60秒 | 保留 |
| v02 | 做饭 | 60秒 | 保留 |
| v03 | 整理工具 | 60秒 | 保留 |
| v04 | 运动动作 | 60秒 | 保留 |
| v05 | 搭积木 | 60秒 | 保留 |
| v06 | 收纳物品 | 60秒 | 保留 |
| v07 | 给植物浇水，前后使用不同容器 | 600秒 | 保留，可做长视频任务 |
| v08 | 多步骤装配过程 | 600秒 | 保留，可做长视频任务 |
| v09 | 与v03完全重复 | 60秒 | 标记重复，不重复构造 |
| v10 | 文件损坏，不能正常解码 | 未知 | 标记失败，不进入构造 |

60秒/600秒只是方便演示，不是项目已经选定的短长视频分界线。

## 3. 模块一：先检查视频，尚不调用 API

程序先登记路径、分配稳定媒体 ID，再读取时长/尺寸并做有界解码检查；在采样画面上检查明显模糊、黑帧、冻结等。通过本地哈希等措施识别重复。

假设 v09 重复、v10 损坏，于是留下 **8 个视频**。原来的 10 个文件都保持不变；“不保留”是指不进入本轮候选清单，不是删除文件。

此时得到：

```text
合格视频清单：v01–v08
媒体参数：每个视频的时长、尺寸、可读性、来源及路径映射
去重/失败记录：v09为什么重复、v10为什么失败
```

**模型调用：0次。** 不接 A10；去重和多样性基础检查仍保留。

## 4. 模块二：先把每个视频变成三级 caption

先只看 v01。程序沿用经过修复/适配的 LLaVA-Video 逻辑，假设按实际时间约每秒取一帧，共得到 60 帧。帧尺寸由配置控制，并记录真实采样时间；这是教师观察视图，不等于学生将来训练时也看60帧。

### 4.1 A1：模型先看局部画面，生成 L1

程序把前10帧和时间顺序发给 Qwen，请它描述画面中发生的事；之后处理下一组，带上必要的局部历史。

```text
请求1：v01的0–10秒附近采样帧 → “人物拿出杯子。”
请求2：v01的10–20秒附近采样帧 → “人物往杯中倒水。”
请求3：v01的20–30秒附近采样帧 → “人物用勺子搅拌杯中液体。”
……
请求6：v01的50–60秒附近采样帧 → “人物整理桌面物品。”
```

这是窗口描述示意，不代表动作恰好持续整个10秒，也不是模型已经被核实正确。真实时间来自程序取帧记录。

v01 得到 **6 条 L1 局部描述**。这些请求输入包含图片，使用视觉能力。

### 4.2 A2：模型读已有描述，形成 L2 和 L3

到约30帧时，程序把已有描述交给 Qwen 做前缀累计汇总。例如：

> 视频前半段，人物准备杯子，倒水后使用勺子搅拌。

全片结束后再次汇总，得到：

> 人物完成准备杯子、倒水、搅拌和整理桌面等操作。

在沿用的官方逻辑里，第一条中途累计汇总保存为 **L2**；最后一次汇总保存为 **L3 全片总结**。最后一次不再同时算一个L2，也不额外再调一次生成L3。

```text
v01：6条L1 + 1条中途L2 + 1条L3
```

A2 只需描述文本，同一个 Qwen API 即可处理，无需再次发送画面。L2 是前缀累计摘要，不是每段相互独立的30秒描述。

### 4.3 其他视频怎么处理

对其余7个合格视频重复上述操作。10分钟视频可以假设采样600帧，按窗口陆续处理，不必一次把600帧塞进请求。

在这一演示的采样/分组规则、无失败重试的条件下：

| 单个视频 | L1视觉请求 | 全部文本汇总请求 | 保存的三级结果 | 合计 |
|---|---:|---:|---|---:|
| 60秒/60帧 | 6 | 2 | 6条L1、1条L2、1条L3 | 8次 |
| 600秒/600帧 | 60 | 20 | 60条L1、19条L2、1条L3 | 80次 |

所以本例6个短片、2个长片的caption阶段约 `6×8 + 2×80 = 208` 次请求。**这是为解释窗口递推计算出的请求数，不是实际账单，也不是全部数据构造只需208次。** 生成题目、CoT、一次审核及上游技术重试另计；不再有A4补标或质量失败后的追加调用。

目前产物是 **8份视频描述底座**，还没有最终训练QA。三级caption统一外置，多个问题复用它，不在每条QA里复制完整三层描述。

代码基础为[LLaVA官方caption脚本](https://huggingface.co/datasets/lmms-lab/LLaVA-Video-178K/blob/6d8c562dc26d70042a0d9704d1cae58c94b89098/gpt4o_caption_prompt/GPT4o_description_prompt.py)。此处使用Qwen、PTS采样与工程包装属于项目适配，不是原代码已经端到端兼容的声明。

## 5. 模块三：描述有了，再生成训练候选

### 5.1 General：A3 根据描述出通用题

程序取出 v01 的相关 L1 和必要摘要，给同一个 Qwen 发**文本请求**：

> 根据这些描述生成动作和先后顺序问题。只生成有描述依据的题；产出中文OE或单选题，单选主要4选1。

可能得到两种候选：

```text
OE：人物倒水后做了什么？
候选答案：用勺子搅拌杯中的液体。

MCQ：人物倒水后做了什么？
A. 打开门
B. 用勺子搅拌杯中的液体
C. 擦窗户
D. 离开房间
候选答案：B
```

这里仅展示两种表达，不要求两道近重复题都发布。A3 还返回任务类型、语言、依据的描述引用；代码后续筛重复与配额。少量题可按配置生成3选1或6选1，始终只有一个正确项。

**A3产出的答案只是候选。** 它读过描述，但没有在此请求中看视频；描述有错，候选也可能有错。是否把候选答案提供给CoT生成器仍待选型，这一步不预先把候选冻结成最终标签。

### 5.2 A4取消：只用已有描述，不补标

如果L1只写“人物处理杯子”，出题器不应强行细化成“搅拌”。当前v1不为它追加取帧或视觉补标请求。

若仍然生成“他在搅拌”的候选，最终A7会看视频；判错、证据不足或无法确认就把该题放入reject，不修caption、不改答案、不回流重生成。**取消补标，仍保留原视频审核。**

### 5.3 Long：A5 把多段事件联系起来出题

再看10分钟的v07。程序只把已经生成的描述按时间整理成候选事件账本，不调用A4补看。假设账本中有：

```text
开头某窗口：人物用喷壶给植物浇水。
中间多个窗口：人物完成其他园艺操作。
结尾某窗口：同一人物用水瓶给对应植物浇水。
```

程序把这些有时间的事件和Long任务要求交给 Qwen（A5文本请求），得到：

```text
问题：视频开头和结尾，人物浇水使用的容器发生了什么变化？
候选答案：从喷壶换成水瓶。
支持位置：开头窗口 + 结尾窗口。
```

仅看某个局部动作无法完成这道比较；需要两处证据。审核还需确认确实是所问对象，不能凭文字假定身份相同。

本题走A5，不再调用A3重新出同一道题。v07本身也可贡献局部动作General题，因此**长视频可以同时贡献General与Long，不是一个MP4只能分到一个文件**。

### 5.4 A6：CoT 预留位置，方法仍待定

选定方法后，程序将问题、选项、所需证据及相应视频视图交给CoT构造器，产出推导标注与结论。所有角色仍可绑定Qwen API；是否需要别的教师，须后续比较，不是当前强制条件。

当前不决定：先答案再CoT，还是先观察/推导再答案；直接视觉四阶段，还是文本初稿后视频修订。**如果CoT还没接入，得到的是QA中间候选，不能称包含CoT的完整交付。**

### 5.5 一个视频为什么会变成多条数据

假设为了演示，每个合格视频生成5道General候选：8个视频得到40道；两个长视频再各生成5道Long候选，得到10道。总共 **50条候选**。

这个“5道”不是生产默认值。有的片子只够1道，有的能出更多；不能为了凑数提出无依据的问题。真正发布前还要删相似题、控制任务覆盖，完成CoT及审核。

## 6. 模块四：一次综合审核，决定候选能否留下

对每条候选，程序在**新的请求上下文**里发给同一个Qwen：

```text
实际视频证据（有时间的帧/片段）
+ 问题与完整选项（若是MCQ）
+ 候选答案
+ 已生成的CoT（待其方法实现）
+ 分项审核要求
```

Qwen一次返回：

- 题目能不能从画面回答，是否有问答不匹配。
- 答案是否受支持，MCQ是否恰好一个正确选项。
- 观察事实、推导和结论是否对应。
- Long题是否具有所要求的多段/全局证据。
- pass或reject，附具体失败原因；任何必需项不足/矛盾/无法判定都reject。

这就是合并后的 **A7**；不再每题拆成原A7/A8/A9三次。它会看到候选答案和CoT，因此不是独立盲答；其通过也不是绝对真值。

程序在审核前按冻结策略准备必要视频视图。长视频要有全局/相关多段覆盖，不能只发两张挑选图片就宣称整片核验完成。证据无法容纳、覆盖不足、无法判定、超时或API失败都直接reject，不追加补看/复核。接口异常记录为audit_error等技术原因，不能与内容错误混算。

本地代码另外检查：12字段结构、唯一ID、路径可读、窗口范围、清洗后文本、选项数量与顺序、重复题和冻结配额等。这些不额外调用Qwen；本地硬检查先失败时可直接reject，不再消耗模型审核。审核发现错误不修改答案，不自动重生成；其他样本继续处理。

## 7. 最后到底得到什么

假设未来CoT方法已接入、必要视频审核及学生适配也都完成，50条候选中出现下面的**虚构结果**：

| 分支 | 候选 | 通过 | reject |
|---|---:|---:|---:|
| General | 40 | 32 | 8 |
| Long | 10 | 7 | 3 |
| 合计 | 50 | 39 | 11 |

此时输出 `general.jsonl` 32行、`long.jsonl` 7行。每行是一道题的训练记录，而不是一个视频的全部内容；相同MP4可被多行引用。

其余11条进入`04_quality/reject/`，保留候选和外部失败原因，不设review队列、不修复救回、不移动原视频。结构正常的拒绝样本可标`quality.verify=reject`；无法解析/结构错误的记录保留原始形状，不能假造合格字段。

最终一行仍只包含既定12项：

| 字段 | 在这条v01的MCQ里怎么来 |
|---|---|
| `id` | 代码分配该题唯一ID |
| `source` | 模块1登记的自有视频来源与v01身份 |
| `conversations` | 完整题干/选项，以及审核后的最终字母B |
| `task` | General分支、事件顺序任务 |
| `question_type` | mcq，4个选项，唯一正确项B |
| `media_info` | 原片60秒、实际使用窗口、caption构造采样摘要 |
| `media` | 原MP4的相对路径；audios/images为空 |
| `modal_mask` | 4 |
| `quality` | 综合审核auto_pass；未校准质量分可为null |
| `cot` | 已选方法生成、通过核验的推导和结论；当前方法仍待定 |
| `language` | 中文；字母B的答案语言沿用题目语言 |
| `tokens` | 按目标GLM实际训练视图/模板计算或明确标记估算；不拿Qwen账单冒充 |

还要外置保存：8份三级caption、事件、具体帧时间、每题依据、API请求/费用、审核详情、去重与划分、失败原因。它们不塞进训练JSON的额外顶层字段。

```text
<外部数据根>/
  01_prepare/       媒体清单、检查与去重
  02_caption/       三级caption、实际帧视图
  03_synthesis/     40条General + 10条Long候选（本例）
  04_quality/       检查详情
    reject/
      samples.jsonl         11条拒绝候选（结构可用时）
      reasons.jsonl         对应失败原因
      invalid_records.jsonl 无法解析/满足结构的原始记录（若有）
  audit/           API与版本记录
  release/<版本>/
    general.jsonl  32条（条件成立后的虚构结果）
    long.jsonl      7条（条件成立后的虚构结果）
```

原MP4仍在原目录。训练媒体路径通过外部root映射到这些原片，不必按问题复制视频。若使用样本窗口，目标读取器必须真的执行该窗口；若CoT被监督，适配器必须把它组装进assistant目标，不能只读取字母B。没有实际GLM processor/template验证时，只能说标注已构造/候选已审核，不能宣称可直接训练或精确token已实测。

## 8. 把每一步对到“谁在做”

| 步骤 | 你/本地程序 | Qwen3.8-Flash | 最直接的产物 |
|---|---|---|---|
| 预清理 | 探测、采样质量、查重复、记录来源 | 不调用 | 8个合格视频清单 |
| 局部描述 | 取帧、附时间、分组发送 | A1看画面 | L1 |
| 递推汇总 | 按进度组织已有描述 | A2读文本 | 中途L2与最终L3 |
| 通用出题 | 选任务、组织描述/题型 | A3读文本出题 | General候选 |
| 长视频出题 | 排列多段事件、选择Long任务 | A5读多段文本出题 | Long候选 |
| CoT | 接口预留，选型后配置 | A6按选定方法生成 | CoT候选 |
| 审核 | 预先组织必要视频证据、检查结构 | A7最多一次综合判断 | 通过或reject，不回流 |
| 发布 | 过滤、计数、路径/监督验证、写12字段 | 不调用 | 两个训练JSONL + 外部记录 |

最重要的三处区别：**视频数不等于题目数；API角色数不等于模型数；候选通过某次模型审核不等于已完成所有训练适配。**
