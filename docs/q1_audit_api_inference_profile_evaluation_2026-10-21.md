# Q1补充评估：按A7审核模型的官方推理配置做审核

日期：2026-10-21。基线：`e7941d660b5d78b3bf33528d509f35301d101a26`。用户已明确：“最后采用的评估模型API”指负责A7质量审核的模型API，不是未来GLM的评测/部署配置。

**结论：你的想法可采用为A7的配置起点，能减少不当预处理和推理设置造成的审核能力损失；不能单独解决Q1中的学生证据可见性，也不自动证明审核准确。建议将两件事拆开：A7按审核模型的官方建议建立并校准审核配置；GLM实际训练输入是否能回答该QA，保留为发布前的独立验收。**

本轮是文献/接口与设计评估，没有选择生产审核模型、修改API参数、调用模型或验证真实视频。具体模型、供应商与协议仍待定。

## 1. 这条思路解决了什么

审核模型的视觉预处理、视频时间编码和解码设置需要配合其实际实现。使用错误的图像尺寸、漏时间信息、意外重复缩放、帧数上限或不适合该模型的生成设置，都可能让审核偏离模型正常能力。

因此，“先查选定模型/供应商的官方推理资料，再建立固定审核配置”比随意指定一组通用FPS/temperature更有依据。官方建议是起点，不是本项目视频事实核验的最优性结论；通用问答、benchmark评测与审核候选答案是不同任务。

Q1无需强制只在上一轮A/B两选项中选择。还可以采用第三种组织方式：**审核配置独立规范化，训练兼容后置验收**。它不增加A7调用轮数，也不恢复A4/A10。

## 3. “推理配置”需要覆盖三层

| 层次 | 应查/应记录的内容 | 未解决时的风险 |
|---|---|---|
| 视觉输入 | 视频/帧列表、实际采样时间与排序、FPS或帧数策略、帧数上限、像素/缩放/裁剪、时间编码、音频开关 | 同一MP4并不等于同一视觉输入；短事件可能漏采 |
| 模型与输出 | 精确模型/版本、provider/endpoint类型、temperature/top_p等支持项、思考模式、上下文及输出预算、结构化输出 | 同名模型可能不同部署；被截断或不完整的审核不能算pass |
| 服务实际行为 | SDK/协议版本、参数是否生效、服务端再采样/resize、可返回的usage或帧元信息、不可观察项 | “请求里写了”不等于“服务实际按此处理”；不支持项不能静默忽略后声称已对齐 |

seed在API不支持时记录为unsupported；支持也不承诺严格可复现。审核模型的内部thinking开关与训练数据的CoT字段是不同层面，本版训练QA仍`cot=null`，不把API思考内容自动写成训练CoT。

权威来源要按问题区分：模型方资料说明推荐的能力设置；实际API供应商资料决定字段、约束与服务行为；开源评测脚本提供可复现参考。快速示例仅能当运行演示。若来源不一致，记录差异并校准，不能挑一个看起来方便的值冒充统一官方结论。

## 4. 为什么它还不能替代学生视图验收

三个对象不同：

```text
caption视图：教师为了描述视频而看到的画面
A7审核视图：审核API按其配置实际看到的画面
GLM训练视图：训练loader按其采样/缩放/processor实际提供的画面
```

即便A7按官方建议正常运行，GLM也可能采用另一种帧数、取帧时刻和分辨率。假设短动作恰好出现在A7的一帧，却落在GLM两帧之间：A7判答案正确完全可能合理，但这份GLM输入缺少回答证据。官方推荐参数无法消除这种输入差异；相同FPS也不保证解码时刻、上限与缩放一致。

这是可构造的输入反例，不是声称某具体API已发生错误。现有发布合同本来就要求学生视图覆盖，故不需要推翻你的方案，也不需要为此把A7强行降到GLM较小的视觉预算。

## 5. 建议采用的完整处理方式

1. **选定A7 API后查官方配置。** 确认模型版本与供应商，分开采集视觉、生成和服务约束；尚缺的项标unknown，不猜。
2. **建立审核配置版本。** 保存来源、适用模型/接口、参数与理由，并区分`official_recommended / api_supported / project_calibrated / unknown`。实际审核视图、请求与响应仍外置，不增加训练JSON字段。
3. **在校准集测试该配置。** 官方建议作基线，只在需要时比较一个有理由的替代配置；以人审错误接受、误拒、证据覆盖与费用选取。校准用独立预算，不是给正式每条QA增加复审调用。
4. **每题仅一次A7正式审核。** 请求前确定全片背景与候选证据视图策略；不在审核失败后提高FPS补发。未通过、证据不足或调用错误遵守原reject规则，不修答案/不补造。
5. **审核通过先成为质量通过候选。** 它证明的是指定审核输入下的自动判断，不意味着GLM训练兼容或绝对事实正确。
6. **发布前做学生适配验收。** 在目标GLM processor/loader配置确定后，实测采样、媒体、token、labels及必要证据可见性；满足现有发布条件才进入训练就绪release。目标配置暂缺时继续保留候选，不强迫现在提供训练工程路径。

### 5.1 后置验收不必新增第二次视觉API，但不能冒充语义证明

本地可检查学生实际帧ID/时间与证据引用、窗口范围、尺寸/裁剪、输入截断等。**时间窗有交集或“采到了附近一帧”只是必要线索，不足以证明动作/实体可见。**

若学生输入保留了A7据以判定的必要画面内容，可建立有依据的支持链；不同采样、破坏细节的缩放/裁剪、或无法观察服务端实际视图时，这条链可能建立不了。不能一律把本地映射成功写成“学生语义验收通过”。

首版建议：能验证的才标训练就绪；不能验证的保留待学生适配状态或按证据不足处理。若未来决定让唯一A7直接包含学生视图，可把语义判定放回同一次调用，但这是可选实现，不是当前自动增加第二轮审核。

### 5.2 API不暴露实际帧时怎么办

记录配置“已请求”与内部输入“不可完全观察”，不伪造帧数或时间。供应商若支持客户端确定的有序视觉帧及可靠时间输入，可以考虑显式送帧，但仍须遵守该模型支持的时序表示、像素上限与服务端缩放。改变输入形式需要重新校准，不能称与原生video_url天然等效。

只有不透明原生视频接口时，仍可生成可追溯到API配置的自动审核候选；不能据此宣称已建立逐帧对齐的学生支持链。这是适配信息的限制，不是断言所有此类候选均错误。

| 项目 | 本轮判断 |
|---|---|
| 决策 | 推荐用选定A7模型/供应商官方建议建立审核配置，再按本项目事实核验任务校准；学生训练兼容保留为独立发布条件 |
| 依据 | 官方资料确有预处理/生成推荐且因模型与接口而异；项目学生配置为空、发布合同已有证据可见性要求 |
| 状态 | 资料为primary-source documented；配置组织与后置验收为proposed；无生产模型参数/审核准确率的runtime验证 |
| 迁移边界 | benchmark推荐不是审核最优；本地开源设置不等于云API实际输入；审核模型正确不等于学生输入充分 |
| 备选 | 唯一A7直接用学生视图；或同次A7分别输入教师/学生视图。前者可能影响审核细节覆盖，后者增加输入费和上下文复杂度 |
| 反证/改变条件 | 官方配置在代表校准集上误判或成本不可接受；服务端输入不可追溯；学生缺关键证据。这些情况触发校准/适配或保持候选，不降低事实门禁 |

Q1的用户意图已经明确：对齐A7审核API。**这可确定配置选择方向，但尚不能将Q1“学生训练输入是否可答”的风险标成已验证关闭。** 也不意味着要改变你已确定的2＋3/1＋2、比例、一次A7、无返工或独立CoT。
